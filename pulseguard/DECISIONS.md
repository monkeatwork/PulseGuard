# DECISIONS.md

Append-only log of autonomous design decisions: what was decided, what was rejected, and why.
Format: `## YYYY-MM-DD — <title>` followed by decision / rejected / why.

## 2026-09-20 — Canonical event schema

**Decided:** JSON payloads over Kafka/Redpanda topics using the schema in `common/pulseguard_common/event_schema.py`:
`event_id, user_id, ts (UTC tz-aware), event_type {mfa_prompt, mfa_decision, login_attempt}, decision {approve, deny, timeout, null}, decision_latency_ms (int|null), src_ip, geo {country, lat, lon}|null, device_id, user_agent, session_id, ingest_ts (UTC, set by collector)`.

**Rejected:** Avro + Schema Registry.

**Why:** Avro/registry adds operational surface (registry service, schema evolution tooling, compiled codecs) with no grading or research payoff for a single-semester project. JSON is sufficient given the data volumes involved and keeps `docker compose up` the only setup step. `ingest_ts` is carried specifically to support clock-skew detection in `latency_drift_slope` (see the 2026-09-20 feature-edge-case entry).

## 2026-09-20 — RBA dataset source: Zenodo, not Kaggle

**Decided:** Fetch the Wiefling RBA dataset from Zenodo record 10.5281/zenodo.6782156 (https://zenodo.org/records/6782156), CC BY 4.0, no authentication required. Query the Zenodo REST API for the file list, stream the download to `data/raw/`, verify the MD5 checksum Zenodo publishes for each file before use, and load with chunked/lazy reads (never a bare full-file `read_csv`). `make data` re-runs the fetch idempotently. On any failure (network, missing record, checksum mismatch) the pipeline halts with an explicit error — no synthetic-benign fallback is built.

**Rejected:** Kaggle (`dasgroup/rba-dataset`) as the primary source; a synthetic-benign fallback generator.

**Why:** Kaggle requires an API token, which blocks an unattended/CI download. Zenodo hosts the same dataset openly. A synthetic fallback was explicitly rejected by the project owner: the FPR metric is a primary reported result, and a fabricated benign baseline would silently undermine it. If the real fetch cannot complete in a given environment, that is a reported, visible failure — not something to route around.

**Resolved file details, confirmed by an actual successful fetch on 2026-09-20:** file `rba-dataset.zip` at `https://zenodo.org/api/records/6782156/files/rba-dataset.zip/content`, 1,093,700,330 bytes, MD5 `cc1b1078b3929650e6c08678caffcc57` — matches the checksum Zenodo's API reports for the record, verified byte-for-byte after download. The zip also contains `LICENSE`, `README.md`, `RESULTS.md`, and preview images alongside the single `rba-dataset.csv` (9,052,907,531 bytes uncompressed); `rba_loader.py`'s single-CSV assumption holds. The CSV's real header matches `RBA_CSV_COLUMNS` exactly: `index, Login Timestamp, User ID, Round-Trip Time [ms], IP Address, Country, Region, City, ASN, User Agent String, Browser Name and Version, OS Name and Version, Device Type, Login Successful, Is Attack IP, Is Account Takeover` — no changes to the column-mapping decision were needed. End-to-end validation: `cli.py --seed 42 --scale 50000` against the real file produced 50,000/50,000 requested users (only 181,434 of ~31M rows needed to be scanned — well under the 2,000,000 cap), 734,168 total events, 100% schema-valid, with profile mix 60.0%/10.0%/9.9%/9.8%/10.3% (plain_benign/benign_high_activity/high_volume_burst/low_and_slow/social_engineering_assisted) — matching the intended 60/10/10/10/10 split closely. Re-running the identical command reproduced an identical `events.parquet` SHA-256, confirming the Phase 1 determinism gate against real data, not just synthetic test fixtures.

## 2026-09-20 — Kafka topic layout / broker choice

**Decided:** Redpanda (Kafka API-compatible, single binary, no Zookeeper) with topics `pulseguard.events.raw` (6 partitions, keyed by `user_id`), `pulseguard.events.enriched`, `pulseguard.alerts`. Consumer groups `feature-engine-v1`, `detection-engine-v1`.

**Rejected:** Apache Kafka + Zookeeper.

**Why:** Redpanda gives the same Faust/kafka-python client compatibility with a single container instead of two, reducing `docker-compose.yml` complexity with no functional loss for this project's scale.

## 2026-09-20 — Burst window and hop window sizing

**Decided:** 10-minute tumbling burst window (matches both the Splunk and Elastic industry baselines exactly, enabling direct comparison). A burst is defined as a run of prompts where consecutive gaps are < 5 minutes. `latency_drift_slope` is computed over a 60-second hop window within a detected burst.

**Rejected:** A single fixed window size shared with the low-and-slow attack profile's pacing.

**Why:** Low-and-slow attacks pace prompts 20–40 minutes apart specifically to stay under fixed-threshold rules. A 5-minute gap-based burst boundary correctly avoids merging paced low-and-slow prompts into one burst, while still matching the 10-minute window industry baselines use, so PulseGuard's numbers are measured on the same yardstick.

## 2026-09-20 — EWMA decay rates

**Decided:** River `EMA(alpha=0.15)` for per-user latency baseline (half-life ≈4.3 events), `EMA(alpha=0.05)` for prompt-rate baseline.

**Rejected:** Fixed 30-event sliding window for both.

**Why:** EWMA decays gracefully from a cold start instead of requiring a full window before producing a signal, and the two alphas reflect that latency is a per-event signal while rate should be evaluated over a longer horizon (days, not events).

## 2026-09-20 — Cohort fallback blending

**Decided:** For users with < 30 observed events, blend `0.5 * cohort_baseline + 0.5 * user_baseline`, weighted by `min(user_n / 30, 1)` linear ramp. Cohort = users sharing the same off-hours/device-novelty segment.

**Rejected:** Hard cutover at exactly n=30 events.

**Why:** A hard cutover creates a metric discontinuity exactly at the cold-start boundary. A linear ramp makes the transition continuous and testable at intermediate points (n=15, n=29).

## 2026-09-20 — `latency_drift_slope` edge cases

**Decided:**
- Single-event burst → `slope=0.0`, `slope_valid=False` (never emit NaN into the model).
- Missing latency (timeout) → excluded from the regression fit; `timeout_flag` tracked separately; `slope_valid=False` if all points are missing.
- Clock skew → slope computed on IdP-issued `ts`, not `ingest_ts`; events whose `ingest_ts - ts` deviates >2s from the rolling per-user median are excluded from the regression and logged as a skew anomaly.
- Out-of-order arrival → a 5-second grace-window buffer per user before a burst's slope is finalized; late arrivals beyond the grace window still update baseline state but do not revise an already-emitted alert.

**Rejected:** Imputing missing latencies; using `ingest_ts` uniformly.

**Why:** Imputation would fabricate signal in exactly the feature CLAUDE.md calls the single most important one in the system — any noise introduced there compromises the project's central claim. Validity bits keep the model informed about missing/invalid data without polluting the regression itself.

## 2026-09-20 — Redis key layout

**Decided:** `pg:baseline:{user_id}:latency`, `pg:baseline:{user_id}:rate`, `pg:burst:{user_id}:current` (sorted set of (ts, decision, latency), TTL 15 min), `pg:cohort:{cohort_id}:latency`.

**Rejected:** A single combined per-user hash key.

**Why:** Separate keys let latency and rate baselines expire/evolve independently and let the burst working-set use a TTL suited to burst detection (15 min) distinct from the long-lived baseline state.

## 2026-09-20 — Stage B (XGBoost) hyperparameters and calibration

**Decided:** `max_depth=5, n_estimators=300, learning_rate=0.05`, early stopping on the validation fold. Isotonic regression for calibration.

**Rejected:** Platt scaling.

**Why:** Tree ensembles typically produce non-sigmoidal score distributions; isotonic regression is monotonic-safe and appropriate given the data volume the generator can produce, whereas Platt scaling assumes a sigmoid relationship that may not hold.

## 2026-09-20 — Stage C (GRU) architecture

**Decided:** 2-layer GRU, hidden_size=64, sequence length = last 20 events per user, dropout=0.2, BCE loss on burst-level label.

**Rejected:** LSTM of equivalent depth.

**Why:** GRU has fewer parameters than LSTM for comparable capacity, which suits the compute budget of a student project, with no expected accuracy loss at this sequence length and data scale.

## 2026-09-20 — Fusion weights and threshold placement

**Decided:** Initial fusion score `= 0.25*StageA + 0.45*StageB + 0.30*StageC`, retuned only via a documented grid search over the validation split (never silently, never touching the test split). Threshold placement: operating point set to match each industry baseline's recall on the validation fold, reporting FPR at that recall for direct comparison, plus a separate best-F1 operating point reported alongside.

**Rejected:** Equal 1/3-1/3-1/3 weighting; a single "optimal F1" threshold with no baseline-matched comparison point.

**Why:** Stage B directly consumes the full response-behaviour feature vector — the project's core contribution — so it is weighted highest by design rather than arbitrarily equalized. Reporting FPR at baseline-matched recall is what makes the industry-baseline comparison meaningful instead of two numbers computed at unrelated operating points.

## 2026-09-20 — Generator latency distributions

**Decided:** Benign approve latency ~ LogNormal(μ=1.6, σ=0.5) seconds (median ≈5s). Fatigue-capitulation latency within a burst modeled as LogNormal with μ decaying linearly by prompt index. Social-engineering lure forces a ~1–2s latency floor at the lure event. All constants named in `benchmark/generator/latency_models.py`.

**Rejected:** Uniform or normal latency distributions.

**Why:** Human response-time data in the published literature is consistently right-skewed (a long tail of slow responses); LogNormal captures this shape, unlike Normal or Uniform, and is the standard choice for reaction-time modeling.

## 2026-09-20 — Train/test split

**Decided:** Split by `user_id` (never by event), 70/15/15 train/val/test, via deterministic `hashlib.md5(user_id)` bucketing, stratified so each split holds a proportional mix of attack profiles and hard negatives.

**Rejected:** Random shuffle split; event-level split.

**Why:** CLAUDE.md's evaluation rule #1 is explicit that event-level splits leak per-user baseline state across the split and inflate every metric. Hash-based bucketing on `user_id` makes the split reproducible across runs without storing split assignments separately.

## 2026-09-20 — Mitigation escalation ceiling (anti-DoS)

**Decided:** Max 1 forced step-up per user per 5-minute cooldown window. After 3 consecutive step-up failures within 30 minutes, escalate to "require alternate factor" — never a full account lock.

**Rejected:** Hard lockout after N failed step-ups.

**Why:** CLAUDE.md's evaluation rule #6 requires the escalation ceiling never lock out the legitimate user under sustained attack. Removing only the vulnerable push channel (while keeping an alternate factor path open) satisfies that literally, whereas a hard lockout would itself become a self-inflicted denial of service.

## 2026-09-20 — Host port remap for local dev machine

**Decided:** `redis` host port 6380 (container 6379), `keycloak` host port 8081 (container 8080), `dashboard` host port 3001 (container 3000). Internal container-to-container traffic on the compose network is unaffected — services still address each other as `redis:6379`, `keycloak:8080`, etc.

**Rejected:** Leaving the default 6379/8080/3000 host bindings.

**Why:** This developer's machine already runs other Docker Compose projects occupying 6379, 8080, and 3000. Remapping only the host-side port avoids a real `docker compose up` failure without touching any in-network service address.

## 2026-09-20 — Dashboard container healthcheck

**Decided:** Use `node -e "require('http').get(...)"` for the dashboard's healthcheck instead of `wget`.

**Rejected:** `wget -q -O- http://localhost:3000`.

**Why:** The `node:20-slim` base image does not include `wget`; the healthcheck failed with "starting" indefinitely until this was caught by actually running `docker compose up` end-to-end (Phase 0 gate) rather than only validating `docker compose config`. Node itself is always present in this image, so it needs no extra package install.

## 2026-09-20 — Confirmed Zenodo record contents; Geo lat/lon made optional

**Decided:** Zenodo record 6782156 contains exactly one file, `rba-dataset.zip` (1,093,700,330 bytes, `md5:cc1b1078b3929650e6c08678caffcc57`), confirmed by querying `https://zenodo.org/api/records/6782156` directly. `rba_loader.py` pins this record id, filename, and checksum as constants and fails loudly if the API ever returns a different file layout. Also: `Geo.lat`/`Geo.lon` in `event_schema.py` are changed from required to `Optional[float] = None`.

**Rejected:** Fabricating lat/lon from country centroids to keep the fields required.

**Why:** The RBA dataset's real columns are `Country`, `Region`, `City`, `ASN` — no coordinates. Inventing coordinates would fabricate signal in exactly the kind of way the "no synthetic fallback" rule for this dataset is meant to prevent. `geo_novelty`/`impossible_travel` features (Phase 3) will operate at country/ASN granularity instead of lat/lon distance; that is a real, disclosed limitation of the benign base layer, not a resolved one.

## 2026-09-20 — RBA dataset column mapping to canonical schema

**Decided:** RBA dataset rows (`Login Timestamp, User ID, Round-Trip Time [ms], IP Address, Country, Region, City, ASN, User Agent String, Browser Name and Version, OS Name and Version, Device Type, Login Successful, Is Attack IP, Is Account Takeover`) map to `PulseGuardEvent` as: `event_type=login_attempt`; `decision=None` and `decision_latency_ms=None` (RBA has no MFA approve/deny/latency data — `Round-Trip Time [ms]` is network RTT, not human decision latency, and is deliberately not conflated with it); `ts` = parsed `Login Timestamp`, assumed UTC; `ingest_ts` = `ts` (no real collector lag exists in historical batch data — skew is only meaningful in generator-produced attack streams, built separately in `attack_profiles.py`); `device_id` = `md5(User Agent String)[:16]` (RBA has no persistent device identifier, so the full UA string is used as a stable per-device fingerprint proxy); `session_id` = a fresh UUID4 per row (RBA has no session concept beyond one login record); `geo.country` = `Country` field, `lat`/`lon` = `None`. Rows where `Is Account Takeover == True` or `Is Attack IP == True` are filtered out of the benign base corpus.

**Rejected:** Keeping RBA's own attack-labeled rows as part of the "benign" base; mapping `Round-Trip Time [ms]` into `decision_latency_ms`.

**Why:** RBA's attack labels target credential-stuffing/account-takeover, which CLAUDE.md places out of scope (general ATO detection is explicitly excluded). Mixing them into the benign base would contaminate the FPR measurement with a different attack class entirely. RTT is a network-layer measurement, not a human reaction time, so treating it as decision latency would misrepresent the response-behaviour feature family the project is built around.

## 2026-09-20 — Attack-profile device/geo modeling and pacing constants

**Decided:** In every attack profile, the `mfa_prompt` event carries the attacker's (novel, unseen) `src_ip`/`device_id`/`user_agent`, while the corresponding `mfa_decision` event carries the victim's own registered device/IP — modeling the real mechanism (an attacker with a stolen password triggers the push; the victim's own authenticator app produces the response). Pacing: high-volume burst = 10-25 prompts, 15-90s gaps (exceeds Splunk's 9-in-10-min); low-and-slow = 6-14 prompts, 20-40 min gaps (stays under Splunk's window and avoids the 5-min burst-merge boundary); social-engineering-assisted = 5-15 prompts, 15-90s gaps, with a lure forcing an immediate approve at roughly the burst's midpoint. Benign deny latency uses its own LogNormal(mu=1.3, sigma=0.4) — faster and tighter than benign approve — since recognizing and dismissing an unexpected prompt is typically quicker than a considered approval. Final capitulation in attack bursts approves with probability 0.85 (attacks mostly succeed, matching the premise that fatigue attacks are effective).

**Rejected:** Identical src_ip/device for prompt and decision events; a single latency distribution for both benign approve and deny.

**Why:** Carrying the attacker's context only on the prompt event is what makes `device_novelty`/`geo_novelty` frequency features (CLAUDE.md's feature table) meaningful signals on the *initiating* event, while the response-behaviour features (latency, drift) remain correctly attributable to the real human on the other end. A single shared latency distribution would erase the deny/approve asymmetry that real user behavior shows.

## 2026-09-20 — User/profile mix ratio and scan bound for `cli.py`

**Decided:** Each RBA user is assigned deterministically (via `sha256(seed:user_id)` bucketing, independent of file iteration order) into: 60% plain benign (their RBA rows only, no MFA events added), 10% benign-high-activity hard negative, 10% high-volume-burst attack, 10% low-and-slow attack, 10% social-engineering-assisted attack. A victim's "own device" context (IP/device/user-agent/country used for `mfa_decision` events and hard-negative sessions) is taken from that user's first-encountered RBA row. `cli.py` scans RBA CSV chunks up to a configurable `--max-rows-scanned` (default 2,000,000) while collecting up to `--scale` distinct benign users, rather than scanning the full ~31M-row file every run.

**Rejected:** An even 20/20/20/20/20 split; scanning the entire file unconditionally.

**Why:** A 60% plain-benign majority keeps the benchmark's base rate realistic (attacks should be the minority case, as in production telemetry) while still guaranteeing enough labelled examples per attack profile and hard-negative case for the classifier to learn from. Hash-based (not order-based) assignment keeps profile mix reproducible even if a future run changes chunk size or file layout. The row-scan cap keeps `make data`'s generation step tractable in development; if a run's `--scale` cannot be satisfied within the cap, `cli.py` reports the shortfall explicitly rather than silently returning fewer users than requested.

## 2026-09-20 — Bug fix: unseeded UUIDs broke generator determinism

**Found:** Two real bugs while writing tests. (1) `attack_profiles.py` built per-burst device/session ids via `uuid.UUID(int=rng.integers(0, 2**63))`, which raises `AttributeError` because `rng.integers` returns a `numpy.int64`, not a Python `int`, and `uuid.UUID` calls `.to_bytes()` on it. (2) `cli.py`'s `finalize_records` assigned `event_id`/login-row `session_id` via unseeded `uuid.uuid4()`, which would silently violate the Phase 1 gate ("same seed -> byte-identical output hash") since every run would get different random ids regardless of seed.

**Fixed:** Added `_rng_uuid(rng)` in `attack_profiles.py`, which builds a UUID from `rng.bytes(16)` (a real Python `bytes` object) instead of `rng.integers`. Added `deterministic_uuid(seed, *parts)` in `seed.py`, which hashes `seed` and content-derived parts (row index, user_id, timestamp) into a UUID; `finalize_records` now uses this instead of `uuid.uuid4()`.

**Why this matters:** Caught by actually running the unit tests rather than only reading the code — the numpy/uuid interaction is a common pitfall that static review would likely have missed. The determinism bug in particular would have silently invalidated the Phase 1 gate: the generator would have "worked" but produced a different corpus on every run regardless of `--seed`, undermining reproducibility that the whole evaluation depends on.

## 2026-09-20 — Bug fix: test directories collided as the same `tests` package

**Found:** `benchmark/tests/`, `eval/tests/`, and `tests/{integration,e2e}/` each had an `__init__.py`, and since neither `benchmark/` nor `eval/` themselves are packages, pytest resolved all of them to the same top-level module name `tests`. Running `pytest benchmark/tests/ eval/tests/` together failed with `ModuleNotFoundError: No module named 'tests.test_metrics_correctness'` — pytest had cached `tests` as whichever directory it imported first and couldn't find the other directory's files under that cached module.

**Fixed:** Removed `__init__.py` from every test directory (`benchmark/tests/`, `eval/tests/`, `tests/integration/`, `tests/e2e/`, and the four `services/*/tests/` stubs). Without `__init__.py`, pytest's default "prepend" import mode treats each test file as a standalone top-level module keyed by its unique basename, which works here since no two test files repo-wide share a filename.

**Why this matters:** This would have silently made whole test directories unreachable together in a single `pytest` invocation (exactly what `make test`/CI does) the moment a second phase added its own `tests/` directory — caught immediately by actually running the combined suite rather than each phase's tests in isolation.

## 2026-09-20 — Phase 2 baseline reproduction on the real generated corpus: results

**Decided:** Ran `eval/harness/run_eval.py` against a real 50,000-user corpus generated from the Zenodo-fetched RBA data (seed 42), evaluated on the frozen test split (3,075 labelled bursts). Full breakdown in `eval/results/baseline_splunk.json` / `baseline_elastic.json`. Headline numbers:

| Baseline | Precision | Recall | FPR | high_volume_burst recall | low_and_slow recall | social_engineering recall |
|---|---|---|---|---|---|---|
| Splunk (>9/10min) | 1.000 | 0.336 | 0.000 | 0.995 | 0.000 | 0.000 |
| Elastic (2 deny+success/10min) | 1.000 | 0.623 | 0.000 | 0.847 | 0.000 | 1.000 |

**Why these numbers, not a bug:** Both baselines score 0% recall on `low_and_slow` by construction — that pacing (20-40 min gaps) is deliberately designed to sit outside any fixed 10-minute window, which is exactly the detection gap response-behaviour features exist to close. Splunk also completely misses `social_engineering_assisted` (0%) because the lure ends the attack in ~5-8 prompts, before volume ever crosses the >9 threshold — while Elastic catches it at 100% because it only needs 2 denials preceding one approval, regardless of overall volume. Elastic actually catches `high_volume_burst` *less* reliably than Splunk (84.7% vs 99.5%) because its 10-minute lookback is anchored to the final approval: in a long high-volume burst, early denials can fall outside that trailing window by the time capitulation happens, whereas Splunk's density-based rule catches any qualifying 10-minute window anywhere in the burst. FPR is 0.000 for both baselines because the current `benign_high_activity` hard negative never denies at all (pure rapid approvals) — a real, disclosed limitation: it proves neither rule misfires on *that* benign pattern, but does not yet test a benign user who occasionally mis-taps a deny before approving. A closer-to-the-boundary hard negative (occasional accidental single denial) is worth adding in a later phase if FPR=0.000 turns out to be too easy a bar once Stage A/B/C are built — flagged here rather than silently tuned around.

## 2026-09-20 — Phase 3 feature-engine design choices

**Decided, several small choices bundled together:**
- **`latency_drift_slope` regression variable:** slope is fit against `prompt_index` (0, 1, 2, ...) within the burst, not wall-clock time. Rejected: regressing against elapsed seconds. Reason: low-and-slow bursts span tens of minutes between prompts, which would put a time-based slope in units of ms-per-second (tiny, hard to threshold consistently across attack profiles with very different pacing); index-based slope ("ms per prompt") is comparable across all three attack profiles regardless of their pacing.
- **Missing/invalid feature values carry an explicit `valid` flag rather than a fabricated 0.0/NaN** (`LatencyDriftResult.valid`, `ApprovalLatencyZ.valid`, `PostBurstApprovalGap.valid`, `DenialLatencyVariance.valid`). Rejected: silently returning 0.0 for "no denials to measure variance over" or "no baseline std yet." Reason: a fabricated 0.0 is indistinguishable from a genuine zero-variance signal to a downstream model; an explicit validity bit lets Stage B (Phase 4) learn to treat "not yet computable" differently from "computed and zero," which matters most for exactly the feature CLAUDE.md calls out as most important.
- **`capitulation_flag` requires a leading deny run of at least `MIN_DENIALS_FOR_CAPITULATION = 2`** before an approval counts as capitulation (not 1). Rejected: firing on a single deny-then-approve. Reason: a single denial before approval is plausibly an honest mis-tap, not fatigue; 2 matches Elastic's own baseline threshold, giving a defensible, industry-precedented cutoff rather than an arbitrary one.
- **`off_hours_flag` uses a fixed UTC hour range (00:00-06:00)**, and **`impossible_travel` falls back to a country-change-within-1-hour heuristic** when lat/lon is unavailable (which is always, for RBA-derived benign events — see the earlier "Geo lat/lon made optional" entry). Rejected: inferring per-user local timezone from country/ASN to compute true local off-hours, and skipping `impossible_travel` entirely when coordinates are missing. Reason: the RBA dataset carries no timezone/offset field, so true local off-hours cannot be computed without fabricating one; a fixed UTC window is a disclosed simplification, not a hidden one. Skipping `impossible_travel` outright would silently drop a frequency feature CLAUDE.md's table requires; a conservative (wide time margin) country-change heuristic keeps the feature populated while being honest that it's coarser than true geodesic distance.
- **Burst/prompt-decision pairing is defensive against overlapping challenges** (`windows.pair_prompts_and_decisions` treats a second `mfa_prompt` arriving before the previous one's decision as an implicit timeout on the first). Rejected: assuming events are always cleanly paired. Reason: the benchmark generator never produces overlapping challenges, but a real IdP stream is not guaranteed to be this clean, and CLAUDE.md's "Architecture" section treats production robustness as a real constraint on L3, not just on the generator.
- **River's `stats.EWMean`/`stats.EWVar` objects are persisted via `pickle`**, not a hand-rolled JSON serialization of their internal state. Verified against the installed `river==0.26.1`: internal state is a private Rust extension object with no stable public introspection API, but round-trips correctly through pickle (tested empirically: update, pickle, unpickle, update again, confirmed the resulting EWMA matches manual calculation). Rejected: reimplementing EWMA/EWVar by hand to get a JSON-serializable state, which would violate CLAUDE.md's explicit mandate to use River for baselines.

## 2026-09-20 — Phase 3 streaming integration test scope

**Decided:** `streaming_app.py`'s Faust/Kafka wiring is exercised through `docker compose up` (the feature-engine container's health check, and later phases' end-to-end dashboard flow) rather than a Testcontainers test that spins up a live Faust worker consuming from a Redpanda topic. What IS covered by a Testcontainers-backed test: `finalize_ready_bursts_for_user` — the actual finalization decision logic (which bursts are grace-window-ready, which get enriched, which stay buffered) — against a real Redis backend, including a 10,000-raw-event throughput check.

**Rejected:** A full Faust-worker-against-real-Kafka integration test asserting on topic output within a timeout.

**Why:** Faust's own consumer-group/rebalancing/at-least-once-delivery correctness is the framework's job, not a claim this project needs to independently re-verify — CLAUDE.md's own emphasis is that "feature computation is pure and unit-testable in isolation from the stream," and the actually novel, project-specific logic (burst finalization timing, feature computation, baseline persistence) is fully covered without needing a live broker+worker lifecycle in the test suite. The Phase 3 gate's "p99 < 200ms" language is about live per-event pipeline latency, which cannot be measured meaningfully without that live broker+worker anyway; the throughput test here instead measures the CPU-bound part directly (10,000 events processed in well under 2 seconds total), which is where that budget is actually spent once Kafka/network overhead is set aside.

**Known gap, flagged rather than silently left:** the `feature_engine` container's `docker-compose.yml` command still runs the Phase 0 FastAPI health stub (`uvicorn app.main:app`), not `streaming_app.py`'s Faust worker (`faust -A services.feature_engine.app.streaming_app worker`). Verified the image still builds correctly with Faust/River/aiokafka added (`docker build -f services/feature_engine/Dockerfile .` succeeds, ~93s, no native-dependency failures on the slim base image). Wiring the actual Faust worker as the live container process — and deciding whether it runs alongside or instead of the health endpoint — is deferred to whichever phase first needs live end-to-end data flowing through `docker compose up` (Stage A/B integration or the dashboard), since no phase gate up to and including Phase 3 requires the container's main process to be the stream processor itself.

## 2026-09-20 — Correction: Phase 4's planned low-and-slow recall target for Stage A/B was wrong

**Found, while building the Stage A/B training pipeline:** the original implementation plan's Phase 4 gate stated "Stage A+B recall on low-and-slow attacks ≥70%." This is inconsistent with the architecture CLAUDE.md itself describes and with how burst segmentation actually behaves on this profile.

`windows.segment_into_bursts` groups events into a burst only when consecutive prompt gaps stay under `BURST_GAP_THRESHOLD_SECONDS` (5 minutes). `low_and_slow`'s pacing is deliberately 20-40 minutes between prompts (`attack_profiles.LOW_AND_SLOW_GAP_SECONDS_RANGE`) — always above that threshold, by design. So a `low_and_slow` generator burst (one `burst_id`, one coordinated attack) decomposes at the feature-engine level into N separate single-event bursts: each individual prompt/decision pair looks, on its own, like an isolated event with `n_prompts=1`, `latency_drift_slope_valid=False` (single-event edge case), and no deny run to speak of. There is no single burst-level feature vector that captures "this is the same slow-paced attack as the prompt 25 minutes ago" — that requires looking across a user's event *sequence* over a longer horizon, which is exactly why CLAUDE.md specifies Stage C (GRU over the event sequence) as the component that "catches low-and-slow." Expecting Stage A/B — which score one burst's feature vector at a time — to independently reach 70% recall on a profile explicitly engineered to defeat burst-level detection contradicts the reason Stage C exists at all.

**Corrected Phase 4 gate:** Stage A/B are evaluated for meaningful recall lift on `high_volume_burst` and `social_engineering_assisted` (both of which stay as single, cohesive multi-event bursts under gap segmentation, so their full response-behaviour signature — deny runs, capitulation, negative drift slope — is visible in one feature vector) at FPR no worse than the Splunk baseline's. `low_and_slow` recall at Stage A/B is reported honestly, whatever it is, and is explicitly *not* held to a target — closing that gap is Stage C's job (Phase 5), evaluated on the same held-out test split for a real before/after comparison.

**`inter_prompt_mean`/`inter_prompt_std` have no paired `_valid` flag** (unlike every response-behaviour feature), so `feature_table.to_model_matrix` fills their `None` (single-event burst) with `0.0` directly. Rejected: adding `_valid` flags for these two as well, matching the response-behaviour convention exactly. Reason: `n_prompts` is always present in the same feature row, and `n_prompts == 1` already fully encodes "these two fields are not applicable" — a tree-based model (Stage B) can learn that conditional relationship directly from the data without a redundant explicit flag, unlike `latency_drift_slope` etc. where invalidity can occur even with `n_prompts > 1` (missing latencies, clock skew) and therefore genuinely needs its own signal.

**Bug fix while writing `test_shap_top3.py`:** the first version of this test's synthetic data let `n_prompts` (a frequency feature) perfectly separate the two classes (8-20 for attacks, always 1 for benign). XGBoost, being a greedy learner, picked that clean signal over the noisier response-behaviour features, so SHAP top-3 was dominated by `n_prompts`/`prompts_per_window`/`inter_prompt_mean` — the test failed, correctly, because it was accidentally testing "does the model use the easiest signal available" rather than "are response-behaviour features load-bearing." Fixed by drawing `n_prompts` from the *same* distribution regardless of label, so frequency carries no signal and the only way to separate the classes is via `deny_run_length`/`latency_drift_slope`/`denial_latency_variance`. A second assertion in that same test file (expecting small SHAP magnitude for an "ordinary" benign case) was also wrong on reflection — a prototypical case of a class can legitimately produce a large-magnitude SHAP value for its most decisive feature; that is what makes it prototypical, not a defect. Replaced with a well-formedness check (finite values, correctly ranked by magnitude) instead of a magnitude bound.

**Bug fix: `attack_profile` NaN vs None broke `breakdown_by_profile`'s benign bucket.** Discovered when the first real Stage A/B training run produced a `"NaN"`-keyed bucket in `eval/results/stage_ab.json` instead of `"benign_high_activity"`. Root cause: `attack_profile` is `None` in-memory for benign rows, but a parquet round-trip of an object column that also holds strings re-reads a missing value as float `NaN`, not Python `None`. `metrics.breakdown_by_profile`'s original `row["attack_profile"] or "benign_high_activity"` silently mis-handled this because `NaN` is truthy in Python (only `0.0` is falsy among floats), so the check never fell through to the sentinel. `run_eval.py`'s baseline path was unaffected — its `burst_ground_truth` already normalized via `pd.notna(...)` before this point — so the Phase 2 baseline numbers already on record are unaffected by this bug. Fixed in two places for defense in depth: `feature_table.build_feature_table` now normalizes `attack_profile` to real `None` at the source (`None if pd.isna(raw_profile) else raw_profile`), and `metrics.breakdown_by_profile` now explicitly checks for both `None` and float NaN rather than relying on truthiness.

**Bug fix: cold-start `approval_latency_z` used a 1ms std floor.** Discovered by looking closely at why the first real Stage A/B run scored recall=1.0 on *every* attack profile (including `low_and_slow`, which per the earlier correction entry should be hard for burst-level features) and an unexpectedly high FPR (19.1%) on the benign hard negative. Root cause: `enrichment.enrich_burst` computed `baseline_std = max(latency_baseline.std_ms, 1.0)` at cold start (every user in the current benchmark is cold-start, since each contributes at most one burst — see the earlier low-and-slow correction entry). A floor of 1 millisecond is absurd next to latencies measured in thousands of milliseconds: it turned `approval_latency_z = (latency_ms - baseline_mean) / 1.0` into essentially the raw millisecond deviation from the mean, disguised as a z-score. Any real approval latency produces a "z-score" in the thousands, so `approval_latency_z` fired as an extreme outlier for *every* approval, benign or not — explaining both the inflated recall and the inflated FPR, entirely independent of whatever the model separately learned from `deny_run_length`/`latency_drift_slope`.

**Fixed:** `CohortBaselineProvider` gained `cohort_std_ms = 3000.0` — the actual standard deviation of the generator's own `LogNormal(mu=1.6, sigma=0.5)` benign approve-latency distribution (`sqrt((e^0.25 - 1) * e^(3.2+0.25)) ≈ 2990ms`, rounded), used as the cold-start floor instead of `1.0`. This makes the cold-start z-score meaningful on the same scale as real latency variability instead of being dominated by an arbitrary tiny denominator.

**Why this matters:** This is exactly the kind of bug that would have silently inflated Stage A/B's reported numbers if not caught before treating them as real results — a textbook case of a metric looking suspiciously good being a red flag rather than a success, caught by re-running the real pipeline end-to-end (not just unit tests with hand-picked values) and refusing to accept a too-good recall=1.0 without explaining it.

## 2026-09-20 — Phase 4 results, and an important honest finding about low_and_slow recall

**Real Stage A+B numbers on the frozen test split** (29,108 gap-based bursts, real 50k-user corpus, after both bugs above were fixed): precision=0.885, recall=0.936, FPR=0.052. Per-profile: `high_volume_burst` recall=1.000, `social_engineering_assisted` recall=1.000, `low_and_slow` recall=0.922, `benign_high_activity` FPR=0.052 (1,064 FP / 20,363 benign). All ≥ the corrected Phase 4 gate (meaningful recall on the two cohesive-burst profiles, FPR below the naive-rule ballpark) — see `eval/results/stage_ab.json`.

**Investigated rather than accepted at face value:** a 92.2% recall on `low_and_slow` looked too high given the earlier architectural finding that individual low-and-slow fragments carry no burst-level signature. A direct query against the trained model confirmed why: of `low_and_slow`'s 7,179 single-event test fragments, 6,532 are lone denials and 647 are the lone final approval (the actual capitulation/compromise event). **Recall on the lone-denial fragments is exactly 1.0. Recall on the lone-approval fragments — the moment an attacker actually gains a session — is exactly 0.0.** The reported 92.2% blended recall is therefore almost entirely the "isolated denial = always attack" artifact already flagged above (no benign example in the current corpus ever contains an isolated denial), not genuine detection of the capitulation moment. Stage A/B is, in the most operationally important sense, currently blind to `low_and_slow`'s actual payload event.

**Reported honestly, not tuned away:** this is not being smoothed over by picking a different threshold or reweighting — no threshold choice changes the fact that a lone approval and a lone denial are the only two feature-vector shapes single-event fragments can take, and nothing in the current feature set distinguishes a low-and-slow attacker's final approval from an ordinary isolated benign approval at the burst level. Two honest implications carried forward rather than hidden: (1) whatever recall number Phase 5's Stage C (sequence model) achieves on `low_and_slow` is the number that actually matters for this attack profile, since only a sequence view can connect a user's prior denied fragments to their later approval; (2) the mitigation controller (Phase 6) may still get practical value out of the early denial detections by acting at the user/session level (flagging a user as elevated-risk after any suspicious fragment, so a step-up challenge is already pending by the time the capitulation approval arrives) even though Stage A/B cannot recognize that specific approval event in isolation — a design implication for Phase 6, not a fix applied here.

## 2026-09-20 — Major finding: Stage C's perfect scores exposed a systemic benchmark gap, fixed with a new hard negative

**Found:** Stage C (GRU over the full per-user event sequence) scored precision=1.0, recall=1.0, FPR=0.0 on the real test split — every single profile, no exceptions. A perfect score across the board is not a result to accept at face value (the same instinct that caught the two bugs above). Analytically confirmed the cause by construction, not just empirically: every attack profile's generator (`generate_high_volume_burst`, `generate_low_and_slow`, `generate_social_engineering_assisted`) always produces **at least one leading denial** before its resolving decision (`HIGH_VOLUME_PROMPT_COUNT_RANGE`/`LOW_AND_SLOW_PROMPT_COUNT_RANGE` both have a minimum well above 1; `social_engineering`'s `lure_index = max(1, int(n*0.5))` is always ≥ 2). Meanwhile `generate_benign_high_activity_session` hardcodes `decision="approve"` for every single step — **zero** benign episodes in the entire corpus ever contain a denial. "Does this sequence contain any denial at all?" is therefore a perfect, deterministic discriminator that requires no learning whatsoever — Stage C's GRU didn't need to learn anything about fatigue, drift, or capitulation to hit 1.0/1.0/0.0; it only needed to notice a `deny` step exists anywhere in the sequence.

**Why this is more serious than the earlier "isolated denial" note:** the same gap was already flagged twice (Phase 2's FPR=0.000 note, and Phase 4's low-and-slow recall investigation), but at the fragment level it only partially inflated results (Stage A/B could see isolated denials in isolation and still missed the capitulation approval, giving a genuinely informative 0%-recall-on-approvals finding). Stage C's whole-sequence view removes that partial protection: it sees the denial AND the later approval together, so it can trivially connect them via the shortcut alone, with no genuine drift/pattern learning required. Left unfixed, this would also have confounded the Phase 8 ablation: `deny_run_length` (classified as a response-behaviour feature) would look artificially load-bearing simply because "any denial present" is doing the discriminating, not because `latency_drift_slope` or other genuine response-behaviour signals are contributing anything.

**Fixed, not just documented:** added a new hard-negative profile, `generate_benign_occasional_denial_session` (`attack_profiles.py`) — a legitimate user who denies **exactly one** prompt (e.g. a mis-tap, or briefly not recognizing a login they themselves just initiated) and later approves a separate, unrelated prompt, both drawn from the same normal benign latency distributions (`sample_benign_deny_latency_ms`/`sample_benign_approve_latency_ms` — no fatigue decay, no capitulation coupling between the two events). This breaks the "any denial = attack" shortcut while remaining a realistic benign pattern, and is deliberately capped at exactly 1 denial — below Elastic's own 2-denial threshold and below every attack profile's minimum leading-denial count — so `deny_run_length`/`capitulation_flag` (which already requires ≥2 denials, see the earlier "MIN_DENIALS_FOR_CAPITULATION" entry) remain meaningful, non-trivial discriminators instead of proxies for a corpus artifact. `cli.py`'s profile mix is rebalanced to 50% plain_benign / 10% benign_high_activity / 10% benign_occasional_denial / 10%/10%/10% attack profiles (`plain_benign` reduced from 60% to make room, all other ratios unchanged).

**All real numbers reported before this fix (Phase 2 baselines, Phase 4 Stage A/B, this Stage C run) are retained in DECISIONS.md as a record of what was found and why it was corrected, not deleted** — but are superseded by a fresh end-to-end regeneration and re-evaluation across every phase now that the hard-negative gap is closed. See the entries below for the corrected numbers.

## 2026-09-20 — Corrected numbers after the hard-negative fix, and why they are more honest, not worse

**Industry baselines (Phase 2), re-run on the corrected corpus:** unchanged — Splunk and Elastic both still report FPR=0.000 (`eval/results/baseline_splunk.json`/`baseline_elastic.json`). This is a genuine, meaningful confirmation, not a coincidence: neither rule's threshold (>9 prompts/10min; 2 denials+approve/10min) is anywhere close to being tripped by a single isolated denial, so both fixed-threshold rules are correctly, provably robust to exactly the case the new hard negative tests.

**Stage A+B (Phase 4), re-run on the corrected corpus:** recall on every attack profile is numerically unchanged (`low_and_slow`=0.922, `high_volume_burst`=1.000, `social_engineering_assisted`=1.000) — but FPR nearly doubled, from 0.052 to **0.088** (1,971 FP / 22,524 benign fragments). Investigated why the recall didn't move at all despite the new hard negative: `low_and_slow`'s own individual denial fragments and `benign_occasional_denial`'s lone denial draw `decision_latency_ms` from the *identical* distribution (`sample_benign_deny_latency_ms` — `low_and_slow` never uses the fatigue-decay sampler for its leading denials, only for the final capitulation approval it doesn't have in isolated-fragment view). This means the two cases are **statistically indistinguishable at the single-fragment level** — not a modeling shortcoming, a real information-theoretic limit of burst-level features. Stage A/B is now forced into an honest precision/recall trade-off instead of the previous free lunch: since there are more `low_and_slow` fragments than `benign_occasional_denial` fragments in the corpus, a model that flags most lone denials still nets positive F1, but the FPR cost is now real and visible instead of structurally zero.

**Why this validates the architecture rather than embarrassing it:** this is exactly the scenario CLAUDE.md's rationale for Stage C describes — a single fragment cannot carry enough information to distinguish an honest denial from an attacker's probe; only a view across a user's event *history* can, by noticing how many such denials occurred and over what pattern. Whatever Stage C achieves on this corrected corpus is now a meaningful test of that claim, not a foregone conclusion from a corpus artifact.

**Stage C (Phase 5), re-run on the corrected corpus: still precision=1.0, recall=1.0, FPR=0.0 — investigated rather than accepted.** Directly measured the raw event count per episode for each profile: `low_and_slow` is always 12-26 events, `benign_occasional_denial` is always exactly 4, `benign_high_activity` is always 30-78. **These three ranges never overlap.** Sequence *length alone* — with no need to examine denial content, latency, or timing at all — still perfectly separates every class. The "any denial present" shortcut from before is gone (confirmed: `low_and_slow`'s own individual denials are now statistically identical to `benign_occasional_denial`'s, as established above), but it has been replaced by a coarser, though more legitimate, shortcut: how many total authentication attempts occurred. This is not purely an artifact in the way the previous one was — a real low-and-slow campaign genuinely does involve materially more attempts than a single accidental denial, so "this user generated an unusually long attempt sequence" is a real, meaningful signal, not a fabricated one. But it is still a blunt volume-based signal that a sequence model could learn without ever using the finer response-behaviour patterns (denial timing structure, latency trends across the sequence) that are the actual point of a GRU over the event sequence, and the current benchmark's disjoint length ranges do not stress-test whether Stage C has learned those finer signals or is only counting steps.

**Reported honestly, next step flagged rather than chased further this session:** distinguishing "did Stage C learn genuine temporal/response patterns" from "did Stage C just learn to threshold on sequence length" would require a harder hard negative whose length range overlaps `low_and_slow`'s (e.g. a benign user with several — not just one — accidental denials spread over a session, mimicking a forgetful user or flaky network) and/or a low-and-slow variant paced with fewer prompts. This is recorded here as a concrete, scoped follow-up for a future iteration rather than pursued further in this session — chasing an ever-harder benchmark indefinitely has diminishing returns against the time already invested, and CLAUDE.md's own evaluation rules (adversarial evaluation, the ablation) are the more appropriate places to continue stress-testing this in Phase 8, once the fusion pipeline itself is complete.

## 2026-09-20 — MANDATORY FLAG: the ablation shows latency_drift_slope adds NO measurable lift

**This is one of the two findings CLAUDE.md requires be surfaced plainly rather than silently resolved or tuned away.** Ran the ablation (`eval/ablation/run_ablation.py`) on the real 50k-user corpus, fragment-level, frozen test split (`eval/results/ablation.json`):

| Variant | Features | Recall | Precision | FPR |
|---|---|---|---|---|
| frequency_only | 9 | 0.888 | 0.329 | 0.703 |
| frequency_plus_response_behaviour (full) | 19 | 0.926 | 0.915 | 0.033 |
| response_behaviour_minus_latency_drift_slope | 17 | 0.926 | 0.915 | 0.033 |

**`latency_drift_slope`'s lift is exactly 0.0 percentage points.** Not "small" — the full model and the model with `latency_drift_slope`/`latency_drift_slope_valid` removed produce byte-for-byte identical predictions on the test split (`tp=8098, fp=753, tn=21771, fn=647` in both). This is confirmed, not approximated, and is not being explained away.

**Why, understood and defensible, not a mystery:** `latency_drift_slope_valid` is `False` for every single-event fragment (per its own edge-case rule — see the Phase 3 entry), and the overwhelming majority of fragments in this corpus *are* single-event, because gap-based segmentation fragments `low_and_slow` (and the two benign hard negatives) into isolated single-prompt pieces (see "Correction: Phase 4's planned low-and-slow recall target was wrong"). The only profiles where `latency_drift_slope` is ever computable at all — `high_volume_burst` and `social_engineering_assisted`, which stay as cohesive multi-event bursts — already reach 100% recall from `deny_run_length`/`capitulation_flag` alone, both of which are unambiguous, saturating signals for a clear deny-run-then-approve pattern. There is no room left for `latency_drift_slope` to add anything on the fragments where it is even defined, and it is undefined everywhere else. The single most important feature CLAUDE.md's design document names is, on this benchmark, informationally redundant given the rest of the response-behaviour feature family and the fragment-level granularity Stage A/B operates at.

**What DOES show a real, substantial lift: the response-behaviour feature family as a whole**, and overwhelmingly through its effect on precision/FPR rather than recall. Frequency-only recall (0.888) is actually not far below the full model's (0.926, +3.8pp) — but frequency-only FPR is **70.3%**, versus the full model's 3.3%. Without `deny_run_length`/`capitulation_flag`/etc., frequency alone cannot distinguish an isolated benign approval from an isolated attack fragment (both have `n_prompts=1`), so a frequency-only classifier is forced to flag the overwhelming majority of ordinary single approvals just to catch the attacks — response-behaviour features are what make the false-positive rate viable at all, which is arguably the more important finding for a project whose evaluation treats FPR as a primary metric (CLAUDE.md, evaluation rule #3).

**Not tuned, not suppressed:** no threshold, weighting, or feature-selection choice was adjusted after seeing this result in order to make `latency_drift_slope` look better. The three variants use identical hyperparameters, identical splits, identical evaluation code (`train_and_evaluate_variant`) — only the input columns differ. A candidate explanation for *why* the slope specifically has no room to contribute (rather than just reporting the number) is offered above precisely so this reads as an understood, structural finding rather than an unexplained gap.

**Recommendation for a future iteration, not attempted here:** `latency_drift_slope` could plausibly matter if Stage A/B operated on the *session* granularity (grouping a user's fragments across their whole history, closer to what Stage C already does) rather than per-fragment, since only then would a burst long enough to have an internal slope regularly exist for `low_and_slow`. That redesign is out of scope for this session's remaining time budget and is recorded here as the concrete next step rather than pursued now.

Given the established findings above — Stage A/B's fragment-level recall is substantially driven by "any isolated denial is an attack" (confirmed in the Phase 4 investigation), and Stage C's perfect scores are substantially driven by episode/sequence length falling in the same disjoint range as the training profiles (confirmed in the Phase 5 investigation) — neither adversarial attacker actually stresses those specific shortcuts, since both still produce a run of several denials followed by one approval, at a length comparable to `low_and_slow`/`high_volume_burst`. **This evaluation demonstrates real robustness to timing-only evasion, which is what CLAUDE.md's adversarial evaluation rule asks for, but it should not be read as evidence of robustness to an adversary who also adapts decision patterns or episode length** (e.g., an attacker who paces one denial at a time across separate, widely-spaced sessions to mimic `benign_occasional_denial`'s length-4 profile specifically) — that is a materially different and harder adversarial scenario, not evaluated here, and is recorded as follow-up work alongside the sequence-length hard-negative recommendation above.

## 2026-09-21 — Wiring the live pipeline end-to-end: real bugs found and fixed

The Phase 3 "known gap" (Faust worker not wired as the live process) and the Phase 7 dashboard-is-empty gap were closed by building a real ingestion replay adapter (`services/ingestion/app/adapters/replay.py` — replays actual labelled episodes from the validated benchmark corpus, since no live IdP exists in this environment), a live scoring worker in `detection_engine` (`live_scorer.py`, consumes enriched events, runs the real trained Stage A/B/C models, writes real `Alert`/`Event` rows), and a live mitigation worker (`live_worker.py`, consumes alerts, runs the real controller, writes real `mitigation_actions`, calls the real webhook). Getting this actually running surfaced several real bugs — recorded here because none of them were caught by the unit/integration test suite, which is itself worth noting: tests that exercise each service's logic in isolation cannot catch bugs that only exist in how services are packaged and wired together at the container level.

**Bug: `ModuleNotFoundError: No module named 'services'` in every service that imports its own code via an absolute path.** Every service's own modules import each other via `services.<name>.app.X` (e.g. `from services.mitigation.app.live_worker import ...`), matching the convention used throughout local development, where pytest runs from the repo root and every top-level package is importable. But each Dockerfile sets `WORKDIR /srv/services/<name>` and never puts `/srv` on the Python path, so these absolute self-imports failed at container startup — a latent bug that unit tests never exercised (they always ran from the repo root) and that Phase 3's own "not yet the live process" status meant nothing had ever actually run this code path as a container's main process before now. Fixed by adding `ENV PYTHONPATH=/srv` to all four affected Dockerfiles (`feature_engine`, `detection_engine`, `mitigation`, `ingestion`).

**Bug: cross-service imports that only worked because the whole repo happens to be on `sys.path` locally.** `services/detection_engine/app/feature_table.py` imports `services.feature_engine.app.baseline_store` and `.enrichment` — needed because Stage A/B training AND the live scorer both build feature vectors the same way the live stream does. But `detection_engine`'s Docker image never copies `services/feature_engine/` (each service's Dockerfile only copies its own directory plus `common/`), so this would have failed the same way `cef_syslog.py` and `windows.py` already had to be moved earlier. Fixed by moving the entire shared feature-computation module set — `cohort_fallback.py`, `features_frequency.py`, `features_response.py`, `baseline_store.py`, `enrichment.py` — into `common/pulseguard_common/`, alongside the earlier `windows.py`/`cef.py` moves. This is now the established pattern in this codebase: anything imported by more than one service's Docker image must live in `pulseguard_common`, never be reached via a `services.<other_service>.app.X` path, because that only ever worked by accident of the local dev environment having the whole repo on `sys.path`.

**Bug: `pulseguard_common.baseline_store` needing `river` was never declared as a dependency of any consumer of the now-shared module.** Once `baseline_store.py` moved into `pulseguard_common`, its `river` import became a transitive dependency of anything importing `feature_table.py` — including `detection_engine`, which had never needed `river` before. Fixed by adding `river` to `pulseguard-common`'s own base dependencies (rather than patching every consumer individually), since it is now genuinely required by code that ships as part of that package.

**Bug: Faust `PartitionsMismatch` crash-looping the feature-engine agent.** `pending_events = app.Table(..., partitions=6)` (matching the original Phase 0 plan's "6 partitions" decision for `pulseguard.events.raw`) requires Faust's co-partitioning invariant: a table must have the same partition count as the source topic its agent consumes. But the topic was never explicitly provisioned with 6 partitions anywhere in code — `ingestion`'s producer just calls `.produce()`, and Redpanda auto-created the topic with its own default (1 partition) the first time a message was produced to it. The agent crashed and Faust's supervisor restarted it in a loop, silently dropping every event produced during the crash window. **Fixed by reducing to `partitions=1`, not by fixing the topic to 6** — a single Faust worker instance (this deployment's actual topology) gains nothing from 6 partitions; that number was a forward-looking assumption from Phase 0 for horizontal scaling that was never exercised, and enforcing it broke the one-worker pipeline for no benefit. Recorded as a correction to the original Phase 0 decision, not a silent reversal.

**Bug (observability, not correctness): module-level loggers in `ingestion`, `detection_engine`, and `mitigation` emitted nothing.** `replay.py`, `live_scorer.py`, and `live_worker.py` all call `logging.getLogger(__name__).info(...)`, but none of the three `main.py` files ever called `logging.basicConfig(...)` — uvicorn configures its own `uvicorn.access`/`uvicorn.error` loggers but not the root logger, so a bare `getLogger(name)` elsewhere in the app has no handler and silently drops every message. Discovered by triggering a real replay and finding zero "Replayed N events" output in `docker compose logs` despite the replay actually working (confirmed independently via Postgres/Kafka state). Fixed by adding one `logging.basicConfig(level=logging.INFO, ...)` call near the top of each of the three `main.py` files.

**Bug (environment, not code): host-to-container port forwarding on this machine intermittently resets or hangs specifically for `POST` requests**, and separately, Docker Desktop's engine itself returned 500s and became briefly unresponsive under the combined load of this project's 9 containers plus ~5 containers from unrelated projects already running on the same machine. Diagnosed by reproducing the same request from inside the container (`docker compose exec ingestion python -c "urllib.request...`), which succeeded immediately where the host-side `curl` had failed or hung — isolating the fault to the host's Docker networking layer, not the application. No code change; noted here because it cost real debugging time and would mislead a future reader into suspecting the `/replay/start` endpoint itself.

**Concrete, scoped follow-up work identified during this build** (not attempted further this session, to respect the time already invested): (1) a harder hard negative with several accidental denials and/or overlapping episode lengths with `low_and_slow`, to determine whether Stage C has learned genuine temporal patterns or only sequence length; (2) evaluating `latency_drift_slope` at session (not fragment) granularity, where it would actually be computable for `low_and_slow`; (3) a decision-pattern-adaptive adversarial attacker, not just a timing-adaptive one; (4) wiring `streaming_app.py`'s Faust worker as the live container process, so the dashboard's already-tested REST API serves real, continuously-updating data end-to-end.

**Bug fix (recurrence of the Phase 2 pytest-collision pattern):** the two new API test files were both named `test_api.py` (`services/detection_engine/tests/` and `services/mitigation/tests/`) — with no `__init__.py` in either directory (per the earlier fix), pytest's rootless import mode requires unique basenames repo-wide, so collecting both together failed with an `import file mismatch`. Renamed to `test_detection_engine_api.py` / `test_mitigation_api.py`. Same root cause as the original Phase 2 entry, worth remembering when adding future test files: check for basename collisions repo-wide, not just within one service's `tests/` directory.

**Secondary artifact flagged, not hidden:** individual `low_and_slow` prompt fragments that are denials are the *only* single-event fragments in the current benchmark that carry `decision=deny` — `benign_high_activity` (the hard negative) never denies (see `attack_profiles.generate_benign_high_activity_session`, hardcoded `decision="approve"`). This means Stage A/B could achieve some non-zero low-and-slow recall on isolated deny fragments via a shortcut ("any lone denial is an attack") rather than genuine response-behaviour drift, since no benign example in the current corpus ever contains an isolated denial. This is the same limitation already flagged under "Phase 2 baseline reproduction on the real generated corpus" (FPR=0.000 because the hard negative never denies) — both point at the same fix (a hard negative that occasionally denies once before approving) as a candidate improvement for a later iteration, not something to quietly work around now.

## 2026-09-21 — Live pipeline verified end-to-end: two final bugs, both in the same seam

The two bugs below are recorded together because they share a root cause worth naming: **both sit in the seam between two components that each had passing tests.** The replay adapter was tested, the feature engine's finalization logic was tested, the detection worker was tested. What was never tested was the handoff — what one component *emits* versus what the next one *assumes*. Both bugs were silent: no exception in the first case, a crash in a background timer in the second. Neither produced a wrong answer; both produced *no* answer, which is harder to notice.

**Bug: replay `speedup` compressed publish pacing but not event timestamps, so no burst could ever finalize.** `replay_burst(..., speedup=N)` divided the wall-clock `time.sleep()` between publishes by `N`, but emitted each event's `ts` at its original historical spacing. The result: with `speedup=20`, events were published over ~30 seconds while carrying timestamps spread across ~10 minutes — every event after the first bore a timestamp in the *future*. The feature engine's grace-window finalization (`windows.is_burst_finalizable`) asks `now > last_prompt_ts + grace`, so it sat waiting for wall-clock time to catch up to timestamps that hadn't happened yet. Bursts never finalized, `pulseguard.events.enriched` was never written to, and the whole pipeline downstream of the feature engine simply never ran — with zero errors logged anywhere, because nothing had gone wrong; the system was correctly waiting. Fixed by compressing the timestamps themselves (`compressed_offset = (original_ts - first_ts) / speedup`) so emitted `ts` values track wall-clock time as the replay proceeds. A docstring on `replay_burst` now spells out this exact trap, because the failure mode (total silence) gives a future reader nothing to search for.

**Bug: the Faust app's `value_serializer="raw"` meant producing a `dict` to the enriched topic raised `TypeError: a bytes-like object is required, not 'dict'` inside the finalize timer.** Once bursts did start finalizing, `enriched_topic.send(value=message)` handed a Python dict straight to aiokafka, which serializes nothing under `raw`. Crucially, this crashed the `@app.timer` task, which Faust escalates to a **full worker crash** (`We experienced a crash! Reraising original exception...`) — so a serialization bug on one message stopped burst finalization for every user in the system. Fixed by serializing explicitly at the producer (`_encode_enriched_message`, `json.dumps(...).encode()`), which is the correct side to fix: `raw` is right for this app because the raw topic carries pydantic's own JSON and `live_scorer.py` already does its own `json.loads`. `default=str` was added as a deliberate safety net — the feature vector is plain floats/bools today, but any datetime or numpy scalar leaking in later would otherwise take down the whole finalize timer again.

One incidental piece of good fortune worth noting: the crash occurred *before* the Redis pipeline that deletes the consumed buffer, so the buffered events survived the crash and were finalized correctly on restart without needing a re-replay. That is accidental rather than designed — the ordering (send, then delete) happens to give at-least-once semantics here, but this was not a considered decision and should not be relied on as one.

**Verified end-to-end result** (`high_volume_burst` episode `-1005089285100268026:...:1580844150`, 11 prompt/decision pairs, replayed at 20x): 22 `events` rows and 1 `alert` row written to Postgres, `fused_score = 0.99999`, and 1 `mitigation_actions` row (`step_up_required`, `consecutive_failures=1`) — the full L1→L5 path, using the real trained models and the real controller, with no fabricated data at any layer. The alert's stored decision sequence is the project's thesis rendered literally: denial latencies of 6315, 6531, 3325, 3028, 3191, 2226, 2308, 1831, 1219, 1457 ms, followed by an **approve at 668 ms**. The SHAP top-3 explanation returned `n_prompts` (frequency), `deny_run_length` (response-behaviour) and `approval_latency_z` (response-behaviour) — i.e. two of the three reasons the system gives a SOC analyst for this live alert come from the response-behaviour family that is the project's contribution.

Note honestly what this does and does not demonstrate: it is a **single episode**, and it confirms the *plumbing* — that every layer runs, connects, and produces the artifacts it is supposed to. It adds no new evidence about detection quality. All quantitative claims about precision, recall and FPR remain the offline harness numbers in `eval/results/`, measured on the by-user held-out split, and the two mandatory disclosures above (zero measured `latency_drift_slope` lift; Stage C's length-confound) stand entirely unchanged by this run.

## 2026-09-21 — Phase 0 gate re-verified: two latent compose/test defects, and a destructive-test hazard

Re-running the full suite after the live-pipeline work turned up 2 failures out of 229 in `tests/integration/test_compose_health.py` (the Phase 0 gate). Both were real defects that had been masked, not flakes — and both had been mis-attributed to "Docker instability" earlier in the session, which is worth recording as a reasoning error: an environment genuinely *was* misbehaving on this machine, and that made it too easy to write off two deterministic failures as more of the same. They reproduced identically every run.

**Defect: the Phase 0 gate connected to Redis on host port 6379, which this compose file does not publish.** `docker-compose.yml` maps `6380:6379` (6379 is routinely already occupied by a local Redis or another project's container — as it in fact was on this machine). The test hardcoded 6379 and failed as a 90-second connection timeout, which presents as a broken or slow container rather than a wrong port number — hence the misdiagnosis. Fixed by hoisting the host-published ports into named module constants (`REDIS_HOST_PORT`, `REDPANDA_HOST_PORT`) with a comment stating explicitly that host-published ports are deliberately *not* the in-container ports, so the next reader does not "helpfully" align them.

**Defect: Redpanda was reachable from the host but unusable from the host, because only its internal listener was advertised.** The broker ran with `--advertise-kafka-addr=PLAINTEXT://redpanda:9092`. A Kafka client does not keep talking to the address it dialed — it asks the broker for the cluster's advertised addresses and reconnects to those. So a host-side `AdminClient` on `localhost:9092` connected fine, was told the broker lives at `redpanda:9092`, and then hung, because that name resolves only inside the compose network. Publishing the port is necessary but not sufficient; the *advertised* address has to be reachable by the client too. This had never surfaced because every other Kafka client in the project (ingestion producer, Faust worker, live scorer, live mitigation worker) runs *inside* the compose network, where `redpanda:9092` is correct — the host-side test was the only client that had ever needed an externally-valid address. Fixed with the standard dual-listener setup: `internal://0.0.0.0:9092` advertised as `redpanda:9092` for in-network clients, `external://0.0.0.0:19092` advertised as `localhost:19092` for host clients, both published. Internal clients are unchanged.

Also corrected in the same test: it created `pulseguard.events.raw` with `num_partitions=6`, contradicting the already-recorded correction to 1 partition (Faust table co-partitioning). Harmless in practice because Redpanda had auto-created the topic with 1 partition long before the test ran and the test tolerates `TOPIC_ALREADY_EXISTS` — but it would have silently provisioned a 6-partition topic on a genuinely clean machine and reintroduced the `PartitionsMismatch` crash-loop, with the misleading appearance that the earlier fix had regressed. Changed to 1, with a comment pointing at the decision.

**Hazard documented, deliberately not fixed: this test destroys a running stack's data.** testcontainers' `DockerCompose.stop()` tears down with `docker compose down --volumes`, which deletes the `pg_data` named volume — every `alerts`/`events`/`mitigation_actions` row from any live run is gone, and the stack is left fully down. This was observed directly: the verified alert from the live-pipeline run above vanished mid-session, which briefly looked like data-integrity loss in the pipeline before the teardown command turned out to be the cause. **Left as-is rather than softened to a volume-preserving `down`**, because the Phase 0 gate's actual claim is "a *clean* checkout comes up with zero manual steps", and a pre-warmed volume would invalidate exactly that. The hazard is now stated in a prominent warning in the test's own docstring instead, since the correct response is "don't run this against data you care about", not "make the gate weaker".

**Final state: 229 Python tests pass, plus the dashboard component tests.** The live pipeline was re-verified after these fixes on a freshly recreated broker, with a *different* attack profile than the first run to confirm repeatability rather than a one-off: `social_engineering_assisted` episode `-1008114484897748134:...:1580737988` (10 events) produced one alert at `fused_score = 0.850` and one `step_up_required` mitigation action. The lower score versus the `high_volume_burst` run (0.99999) is the expected direction — that profile is deliberately subtler and shorter — though with one episode each this is an observation about two data points, not a measured result; the reportable numbers remain the offline harness ones in `eval/results/`.

## 2026-09-21 — Negative control on the live path, and a granularity mismatch that must NOT be tuned away

Verifying the live pipeline against attacks only would have been worthless — four detections prove nothing without a negative control — so benign `benign_high_activity` episodes (the hard negative) were replayed through the identical path. Results, and one genuine problem.

**Defect found and fixed: `live_scorer.py` had no alert threshold at all.** Every scored burst was written to `alerts` and republished to `pulseguard.alerts` regardless of score, including a benign burst that correctly scored **0.0012**. The model was right; the plumbing ignored it. This matters because `alerts` is the SOC analyst's work queue — the thing the whole L5 dashboard exists to present — and an ungated queue makes it a log tail in which real detections are buried. Fixed by gating on `ALERT_THRESHOLD`, defaulted to **0.01: the frozen full-fusion operating point from `eval/results/full_fusion.json`**, i.e. the same threshold every reported precision/recall/FPR number was measured at, not a fresh number invented for the live path. `events` rows are still written unconditionally — that is telemetry and belongs in the hypertable regardless of whether an alert was raised — so only the alert queue is gated.

**The real finding: the frozen operating point does not transfer to the live path, because the live path scores at a different granularity than the evaluation did.** With the gate in place, benign `benign_high_activity` fragments scored **~0.050–0.056** — comfortably above the 0.01 threshold, so they still raise alerts. Offline, that same threshold measured `fpr = 0.000` on 1537 benign episodes. Both numbers are correct; they are not measuring the same object. The offline harness scores one **episode** (a whole session as the generator labelled it), while the live feature engine scores **gap-segmented fragments** (`BURST_GAP_THRESHOLD_SECONDS` = 5 min). A benign high-activity user's 30 logins spread across a day segment into many single-login fragments, each scored independently, and a fragment's score distribution is simply not the distribution the threshold was tuned against.

This is the **same root cause already disclosed for `latency_drift_slope`** — evaluation granularity (episode) differing from streaming granularity (fragment) — now showing up a second time, in a second place, with an operational consequence rather than a measurement one. That recurrence is the most useful thing this verification produced: it reframes the granularity mismatch from a quirk affecting one feature into a systemic property of the current architecture.

**Deliberately NOT fixed by raising the threshold.** Setting `ALERT_THRESHOLD` to ~0.1 would have made the live demo produce clean output immediately, and would have been exactly the "tune the evaluation until the feature looks good" move ruled out at the start of this project. The threshold would then correspond to nothing that was ever measured, and the reported FPR would no longer describe the running system. The honest position is: 0.01 is the evaluated operating point, it is retained, and the mismatch is reported. Anyone re-tuning it must first re-run the harness at fragment granularity, which is the actual fix and is recorded below as follow-up work.

**What did hold, and it is the safety-critical part: no false mitigation.** `mitigation_actions` remained **empty** across every benign replay. The live mitigation worker gates independently at `MITIGATION_CONSIDERATION_THRESHOLD = 0.3`, so benign fragments scoring ~0.05 produced no step-up, no escalation, no action of any kind — while all four attack episodes (two `high_volume_burst` at `fused_score = 1.000`, two `social_engineering_assisted` at 0.841 and 0.864) each produced exactly one `step_up_required`. The two independent gates turn out to matter: the alerting gate was broken and the mitigation gate still prevented any user-visible harm. That is defence in depth working as intended rather than by luck, since the 0.3 threshold was chosen deliberately (recorded earlier as "lower than a confirmed-attack threshold, because the controller escalates rather than acts immediately").

**Follow-up work this adds** (scoped, not attempted): re-run the frozen harness at **fragment** granularity to establish an operating point the live path can legitimately use, and/or aggregate fragments back to session granularity in the feature engine before scoring so the live path matches what was evaluated. The second is the more principled fix and would simultaneously make `latency_drift_slope` computable where it currently is not — the two disclosed problems likely have one shared solution. Until one of those is done, the live pipeline should be described as demonstrating the end-to-end path, with all quantitative claims coming from the offline harness.

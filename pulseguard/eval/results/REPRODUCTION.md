## Notes

- Corpus: `make generate SEED=42` reproduced the committed demo slice (`data/demo/demo_events.parquet`) row for row. The `events.parquet` file SHA-256 differs from the one recorded in `operating_point.json` (a1f84f... vs 71637a...) only because a different pyarrow version (26.0.0) writes different file metadata; the content is the same.
- Environment: macOS (Apple silicon), Python 3.12.14, pandas 3.1.0, pyarrow 26.0.0, xgboost 3.4.1, torch 2.14.1, scikit-learn as pinned by requirements-dev.txt.
- Two fixes were needed to run the pipeline on macOS at all; neither changes any computation. (1) torch and xgboost each bundle an OpenMP runtime: with torch loaded first, xgboost segfaulted in `tune_fusion_weights`; with xgboost first, torch's GRU training deadlocked. `services/detection_engine/app/__init__.py` now loads xgboost first and keeps torch on one thread on macOS. (2) `eval/adversarial/run_adversarial_eval.py` imported torch without using it, which triggered the same crash; the import was removed.
- Stage C's validation-chosen threshold is the one value that differs (0.76 here vs 0.74 committed), with identical test metrics. Both runs on this machine (one multi-threaded before the OpenMP fix, one single-threaded after it) picked 0.76, so the difference comes from the platform or library versions (macOS/arm64, torch 2.14 vs the Linux run that produced the committed models), not from threading. The deployed model files in `model_registry/` were left as committed.
- Tests: 235 passed. 28 errors, all in tests that start containers through testcontainers (Docker was not running on this machine): detection-engine API (9), live scorer (1), feature-engine baseline store (5) and streaming app (4), ingestion adapters (2), mitigation API (5) and integration (2). They were not run, not failing.
- Conclusion: the committed numbers are reproducible from the code and seed. Reproducible is not the same as trustworthy: the benchmark's latency signal is generated (HANDOFF.md), which is what the fatigue sweep tests.
